# API-тестування як жива документація

## Концепція

Файл `server/scripts/test-stage-d.js` є **живою документацією** API: замість статичного опису він виконує реальні HTTP-виклики до сервера і перевіряє їх результат.

Підхід відповідає ідеї *executable specification* — специфікація, яку можна запустити та отримати конкретний (зелений або червоний) результат. Скрипт одночасно виступає:

- **прикладом коду** — показує правильну структуру запитів (метод, заголовки, тіло);
- **контрактною перевіркою** — підтверджує, що API повертає очікувані формати відповідей;
- **регресійним тестом** — при будь-якому рефакторингу серверного коду можна швидко переконатися, що публічний контракт не зламано.

---

## Що саме перевіряє скрипт

| Крок | Ендпоінт | Очікуваний результат |
|------|----------|----------------------|
| 1 | `GET /api/health` | Сервер відповідає 200 |
| 2 | `POST /api/auth/register` | Повертає `{ token }` |
| 3 | `GET /api/auth/me` з Bearer-токеном | Повертає `{ id, email }` |
| 4 | `GET /api/products` | Масив товарів (може бути порожнім) |
| 5 | `GET /api/exercises` | Масив вправ (може бути порожнім) |
| 6 | `POST /api/favorites/products/:id` + `GET /api/favorites/products` | Товар присутній у списку вибраного |
| 7 | `POST /api/favorites/exercises/:id` + `GET /api/favorites/exercises` | Вправа присутня у списку вибраного |
| 8 | Фінальний `GET` обох списків | Дані відповідають доданим записам |

Скрипт генерує унікальну тестову електронну адресу (`test-<timestamp>-<random>@msportfit.test`) при кожному запуску, що забезпечує ізоляцію тестів без ручного очищення бази даних.

---

## Як запустити

З директорії `server/`:

```bash
npm run test:stage-d
```

Або з кореня монорепозиторію:

```bash
npm --prefix server run test:stage-d
```

> **Передумови:** сервер має бути запущений (`npm run dev` у `server/`) і база даних — засіяна тестовими даними (`npm run seed`). Детальніше про налаштування середовища — у `README.md`.
